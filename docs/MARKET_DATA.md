# Market data: sources, limitations and going live

FC 27 Market Engine **does not have access to live FC 27 transfer-market prices** out of the
box, and it never pretends to. Every price in the database carries the source it came from,
and the UI labels it everywhere it is shown.

## Data sources

| Source      | Label in UI    | Where it comes from                                                                 |
|-------------|----------------|-------------------------------------------------------------------------------------|
| `manual`    | Manual         | Typed in by you (Price History page, watchlist "current price", player detail page) |
| `csv`       | CSV import     | A CSV file you upload on the Price History page                                     |
| `sample`    | Demo sample    | Seeded with demo accounts. Invented numbers for generic placeholder players         |
| `simulated` | Simulated      | Generated by **Simulate market move**: a ±4% random walk, for practice only         |
| `live`      | Live           | Fetched from an authorised provider you configure (see below)                       |

The header shows an overall **LIVE / MANUAL / SIMULATED / NO DATA** indicator, based on the
source of the most recent observation on your preferred platform, plus the time of the last
update. Prices older than **Stale after (hours)** (Settings, default 24h) are flagged as stale.
The scanner returns **WATCH** instead of a trading signal while data is stale, and a
`stale_data` alert is raised.

### What the demo data is (and is not)

"Meta Gold Winger" and "High-Rated Fodder 88" are **generic demo records**, not real FC 27
cards. Their price histories are generated so that the documented example works exactly
(historical low 25,000, high 32,000, current 25,200 → BUY). They say nothing about any real
player's price.

## FUTBIN and FUT.GG

FUTBIN and FUT.GG don't offer a public API for third-party apps. EA's FC Community
API is limited to sites EA has approved, and works by signing in with an EA account on
those sites. It isn't something this app can call. Scraping their pages would likely
breach their terms and copy EA card artwork, so the app doesn't do it.

What the app does instead:

* **Links**: each card can store its FUTBIN and FUT.GG page (Card Gallery → ✎, or the
  player page). Only `https://` addresses on `futbin.com` / `fut.gg` are accepted. Until a
  page is saved, the button runs a search restricted to that site.
* **Seen on**: manual prices record where you read them (in-game market, FUTBIN, FUT.GG,
  other), shown as "via FUTBIN" etc. next to the price. They remain `manual` data: the app
  has not verified them.
* **Screenshot import**: the practical way to use their player data. Screenshot the page
  you're viewing (or a price card posted in a trading group) and upload it on **Screenshot
  Import**. Claude (`claude-opus-5-5`, structured output) reads each player, rating, position
  and console price, you tick the rows that are right, and only those are saved as `manual`
  prices with *seen on* set to the site. The image is not stored. Reads are logged and
  capped per desk and site-wide per day, because each one is a paid API call.
* **No crawling**: the app does not fetch or scrape either site. Both block automated access,
  and getting around that would mean disguising the traffic. A crawler would also break
  whenever their page layouts change.
* **Images**: a card image is a URL you provide. Use images you have the right to use.

If you obtain licensed access to a price feed (from one of these sites or anyone else),
connect it through the provider adapter below.

## How prices are used

* **Historical low / high**: min / max of observations in the last **30 days** on your
  preferred platform. At least **3 observations** are required; with fewer, the signal is
  WATCH.
* **Current price**: the most recent observation.
* **Volatility**: the coefficient of variation of the same window. Above **Max volatility**
  (default 25%) the signal is RISK.
* **Active transfers**: valued at the newer of your own estimate or the latest market
  observation, falling back to the purchase price ("At cost").

Signals are rules applied to the data you provide. Past prices do not guarantee future
selling prices, and no estimate is a guaranteed profit.

## CSV format

```csv
player_name,price,observed_at,platform,version,rating
Meta Gold Winger,25400,2026-10-10T09:00:00Z,cross,Demo Gold Rare,86
```

* Required: `player_name`, `price` (whole coins, 1 to 15,000,000).
* Optional: `observed_at` (ISO 8601, `DD/MM/YYYY HH:MM` or `DD/MM/YYYY`; defaults to now;
  UTC if no offset), `platform` (`cross`, `playstation`, `xbox`, `pc`), `version`, `rating`.
* Each card is identified by player name + version + rating. Rows that fail validation
  (bad numbers, future timestamps, unknown platform) are skipped and reported. Valid rows
  are still imported.
* Up to 5,000 rows / 2 MB per upload.

## Switching to an authorised live data provider

The app talks to live data only through a provider adapter (`MarketDataProvider` in
`backend/app/services/market_data.py`). Only use a data source whose terms allow this
use. **Do not scrape EA's web app or companion app, or automate the in-game transfer
market.** That is against EA's terms of service and can get accounts banned. The app
never places trades: purchases and sales are either simulated or recorded by you.

### Option A: the built-in `http_json` adapter

If your provider exposes, or you put a small proxy in front of it that exposes, this
contract:

```
GET {MARKET_DATA_API_URL}?platform=<cross|playstation|xbox|pc>&cards=<card_key,card_key,...>
Authorization: Bearer {MARKET_DATA_API_KEY}

200 OK
{
  "prices": [
    { "card_key": "meta-gold-winger-demo-gold-rare-86", "price": 25200, "observed_at": "2026-10-10T12:00:00Z" }
  ]
}
```

then configure:

```bash
MARKET_DATA_PROVIDER=http_json
MARKET_DATA_API_URL=https://your-provider.example/prices
MARKET_DATA_API_KEY=...            # keep out of git; use your host's secret store
MARKET_DATA_TIMEOUT_SECONDS=10
```

`card_key` is shown on each card (`/api/market/cards`). It is derived from player name,
version and rating. If your provider uses its own IDs, map them in your proxy. Malformed
rows (missing fields, non-positive prices) are dropped, not stored.

Once configured, **Refresh live** on the Price History page (or `POST /api/market/refresh`)
fetches prices for every card you track and stores them as `source = live`. The indicator
switches to **LIVE** only when the newest observation really came from the provider.

### Option B: a custom adapter

1. Implement the protocol in `backend/app/services/market_data.py`:

   ```python
   class MyProvider:
       name = "my_provider"
       def fetch(self, card_keys: list[str], platform: str) -> list[ProviderQuote]: ...
   ```

2. Return it from `get_live_provider()` when `MARKET_DATA_PROVIDER=my_provider`.
3. Add a test like `test_live_provider_contract` in `backend/tests/test_api.py`, using
   `httpx.MockTransport` so the suite never calls the real service.

### Scheduling refreshes

The app refreshes when a user clicks **Refresh live**. For unattended refreshes, call
`POST /api/market/refresh` for each user from a scheduler (cron, a platform job), respecting
your provider's rate limits. The **Refresh every (minutes)** setting is stored for that job
to read. The app does not run a background poller by itself.

### Moving a demo deployment to live data

1. Set `SEED_DEMO_USER=false` and `ALLOW_DEMO_SIGNUP=false`, so no new demo accounts or
   sample data are created.
2. Configure the provider (Option A or B) and restart.
3. Real users register normal accounts. Their watchlists start empty, so no sample prices
   are mixed into their data.
4. Existing demo accounts keep their sample data, which stays labelled "Demo sample". Delete
   those users from the database if you don't want them.
